## Change your password from inside your account

**`/account/` → Password**, a folding section like the rest, last in the
quick-jump bar.
[functions/api/auth/change-password.ts](../functions/api/auth/change-password.ts)

- Asks for the current password, the new one twice, and has a
  **show-what-I'm-typing** toggle — entering a password you can't see,
  twice, is how a typo becomes an account you can't get into.
- The current password is required even though the session already
  proves who you are: a session can be left open on a shared machine,
  and one question means a passer-by can't take an account over with two
  clicks. Checked against Supabase Auth exactly as signing in checks it.
- Minimum 8 characters, matching registration and the reset flow.

The emailed-code flow at `/reset-password/` stays for what it's actually
for: someone locked out who can't sign in at all.

## The night the reset flow ate an hour

Tina couldn't sign in. Getting her back in took far longer than it
should have, and every delay came from the same habit in this code:
**a step that fails quietly and reports success.** Four of them, stacked.

### 1. Only the newest code counted — fixed
[functions/api/auth/reset.ts](../functions/api/auth/reset.ts) honoured
only the most recent un-consumed code for an address. But reaching the
code-entry screen *requires asking for a code*, so a code already in the
inbox was dead before it could be typed — and the page called it
"invalid or expired", which is a lie about a perfectly good code.

Now any un-consumed, unexpired code works. Each is single-use, all die
inside the same 15-minute window, and every outstanding code for the
address is burned the moment one succeeds. **Attempts are summed across
the live codes**, so asking for more can't widen the guessing budget.

### 2. The address was buried — fixed
The confirmation read *"If an account exists for **x**, a six-digit code
is on its way"*, which scans as success. Chrome had autofilled the field
with `theiagoodner@gmail.com` — an address Tina has never owned. Step 1
looked that up, found nothing, said "on its way", and sent nothing.

The address now sits on its own line at full size under **Code sent to**,
with *Not your address? Start over* beside it — and that button **empties
the field first**, because autofill will otherwise put the same wrong
address straight back.

It still cannot say "no account here". That would let anyone test who
belongs to this parish. The address itself has to carry that warning,
which is exactly why it has to be readable.

### 3 and 4. Still silent — worth fixing
- **A failed Resend call is only `console.error`'d**
  ([forgot.ts](../functions/api/auth/forgot.ts)), and the page still says
  "sent". If the key ever expires, nobody will be told.
- **The rate limit is silent**: `MAX_CODES_PER_WINDOW = 3` per
  `CODE_TTL_MS` (15 min), in
  [src/lib/reset-code.ts](../src/lib/reset-code.ts). Over the cap, the
  page reports "sent" and sends nothing. Both limits are tight for mail
  that can take minutes to arrive.

### What this cost, and the lesson
Hours, and most of it spent on my wrong guesses — expired code, wrong
domain, user error — because no layer would say what had happened. The
Resend **Emails** log settled it in one screenshot: exactly one reset
email existed, the one sent by curl. Her presses had produced nothing at
all, which pointed straight at the address.

**Check the Resend log first.** It is the only honest witness in this
flow.

## Coffee hour says whether it's a fast day

[src/pages/coffee-hour.astro](../src/pages/coffee-hour.astro) — each
Sunday now reads:

> Sunday, September 27, 2026 · **Fast Day — Food with Oil**

- `Fast Day` (purple), `Fish Allowed` (blue), `No Fast` (green) — the
  same words and colours as the calendar banner.
- The rule rides along **only on a fast day**; on a fish day the rule
  *is* "Fish Allowed" and it would read twice. The calendar page drops
  it for the same reason.
- Same size and weight as the date, only colour setting it apart.
- Read from `/api/calendar?date=…`, the same endpoint the calendar page
  uses, so the two can never disagree. Edge-cached an hour.
- Loaded **after** the sign-up list is drawn — eight lookups shouldn't
  hold up the sheet — and a Sunday the calendar can't answer for shows
  **nothing** rather than a guess.

Why it can't be worked out from the date: Sundays are not uniformly
fast-free. Inside Great Lent and the Nativity fast they carry a rule of
their own. Verified against the live calendar — 27 Sep 2026 is a fast
Sunday with oil; 20 Dec 2026 is fish.

## 25 September — catechism lessons are searchable

**Migration 017 applied.** `catechism_lessons` now has the same text
columns `library_books` got in 015 and 016: `text_content`,
`text_chars`, `text_status`, `text_pages`, `text_extracted_at`.

Before this, lessons could not be searched at all — not even by title.
Finding a passage meant remembering which lesson held it.

**All 16 existing lessons were backfilled the day it shipped** and read
`Yes · N pages` in the admin Searchable column.

### How it fits together
- **Extraction** — [src/lib/pdf-text.ts](../src/lib/pdf-text.ts), now
  shared by the library uploader and the catechism uploader, so the
  text, the page markers (`␞printedLabel|pdfPage␞`) and what counts as a
  scan cannot drift apart between them. Runs in the admin's browser: a
  Function's CPU budget will not read a PDF.
- **New uploads read themselves** on `/admin/catechism/`. A scan is
  recorded as `empty` rather than treated as a failure, and the upload
  carries on regardless — a lesson nobody can search still beats no
  lesson.
- **Backfill** — "Make N lessons searchable" on `/admin/catechism/`,
  hidden when there is nothing to do, beside a **Searchable** column.
- **[functions/api/catechism/search.ts](../functions/api/catechism/search.ts)**
  searches titles, teachers, series, descriptions *and* the text inside
  each lesson. Server-side on purpose: doing it in the browser would
  mean sending every lesson's full text to every member on every page
  load. Results carry the matching passage and its page, because a
  lesson appearing for a word that is nowhere on its row reads as a bug.
  Same loosening rule as the library search, including the two-word
  floor.
- **[functions/api/catechism/text.ts](../functions/api/catechism/text.ts)**
  serves one lesson's text, with the lesson visibility rules: members
  see posted lessons, drafts are admin-only, logged-out visitors get
  nothing.
- **Reader** — `/account/lesson/` gains a **Text** view with a sticky
  find bar and page dividers. The pages are canvases, so the browser's
  own Ctrl+F finds nothing in them; Ctrl+F is redirected to the text
  when there is text. The text loads *before* the PDF and is never
  waited on, so a slow or broken PDF cannot take the readable words
  down with it.
- **My Learning** gains a search box with the matching passage and page
  under each result.

### The reading surface
The reader's dark frame exists so white PDF pages stand out. The text
view inherited it and became pale type on charcoal — fine to glance at,
punishing to read, which is the one thing that view is for. It now sits
on white with near-black text as its own sheet: **17.8:1** for body
text, **8.4:1** for the current search hit (gold, with a ring so Next
and Previous are followable). Written as plain CSS on `#text-view`
rather than theme tokens, because this sheet must stay light whichever
theme the site is in. The frame around it stays dark for the pages.

  poll for the actual text you changed.

  books to exist in more than one place. Readership is not the point.

  Sep cost an hour of theories — expired code, wrong domain, too many

  the page's own echoed address settled it in one look. "I don't know
  yet" is a better answer than a theory that sounds like one.
